# Architecture

A walk through the main subsystems: what each one does, where it lives and how it talks to the rest. The owning README for each part is named in its section and holds the detail, including the focused tests to run after a change.

## The shape of the system

```
 Microsoft 365                       server                                  people
 ─────────────                       ──────                                  ──────
 Exchange mailbox ─ change ─► Azure Function ─► storage queue ◄─ polled ─┐
                   notification                                          │
                                                       mail intake + triage workers
 SharePoint / OneDrive ◄──── Graph files ────┐                           │
                                             │                           ▼
 Drafts folder ◄── drafts only ── Graph mail ┤      ops DB (SQLite) ◄── job queue
                                             │           ▲
                                     domain code (tools/)│
                                             │           │
                                  Hub API (FastAPI) ─────┴──► clientdb (Postgres)
                                             ▲
                                             │ bearer token + Remote-User
                                  CRM (Next.js server routes) ◄── browser ── caseworker
                                             │
                                  Documenso (self-hosted) ── signing links in drafts ──► client
                                  model_backend ──► OpenRouter (zero data retention)
```

Python domain code lives under `tools/`, which is a flat import namespace (scripts import siblings as `import clientdb_sql`). The front ends live under `products/`. Deployment lives under `deploy/`: systemd units in `deploy/systemd/` and the Ansible playbooks, roles and group variables in `deploy/ansible/`.

## Firm profile

`profile/` and `tools/firm_profile.py`.

One YAML file describes the firm a deployment serves: its name, mail and web domains, the firm's people, the folder books, the client-files library root, the OneDrive root name, the SharePoint site id, the Key Vault name (never its secrets), the access team domain, the app hostnames, and the legal-representative and statement-of-truth details that court forms print.

- `load_profile()` returns a frozen `FirmProfile`. It reads the `path` argument first, then the file `CASEFORGE_FIRM_PROFILE` names (a set variable pointing at no file is an error, never a fallback), then `profile/firm.yaml`.
- The file is parsed with PyYAML `safe_load` and validated against `profile/schema.json` (JSON Schema draft 2020-12). Every field is required and unknown fields are refused. The error names the first failing field.
- `profile/firm.example.yaml` is a fully synthetic firm and the starting point for a real one.
- The CRM has its own firm values in `lib/firm.ts`, overridden at build time by `NEXT_PUBLIC_FIRM_*` variables. Its demo data comes from a fictional firm.

Each kind of setting has one home: firm details in the profile, secrets in environment variables (loaded from Key Vault by `tools/load_kv_secrets.py`), tunables in environment variables only where the code default does not suit, servers in the Ansible inventory, and what runs on the production box in Ansible group variables. `.env.example` is generated by `tools/maintenance/env_inventory.py --write-example`, and a test fails when code reads a variable that file does not list.

## Hub API

`tools/vergil/api.py`.

A FastAPI service in front of the domain modules in `tools/vergil/`, which are plain importable Python with no UI framework, so each can be tested directly. It serves client search, retrieval, the casework-record endpoints and the `/client-viewer/*` routes the CRM uses: client edits, parties and children, flags, hearings, billing, attendance notes, Case flow, attention items, drafts, the Today board and system health.

- **Authentication.** A bearer token. A caller may pass a `Remote-User` identity, which the CRM sets from a verified Cloudflare Access JWT. A caller with a valid token and no identity (a script, a timer) shares one pooled identity.
- **Client-exposure budget.** List and search endpoints run the rows they are about to return through `enforce_client_exposure_budget`, which counts distinct client records per identity over a rolling 24 hours and writes an audit record. As configured it assesses and logs but does not block. The audit trail answers what an account looked up and whether it crossed a threshold.
- **Write attribution.** Every database write names its actor as "typed name via hub path", from the request's `edited_by` or `by` field, else `Remote-User`. That actor lands in the SQL change log.

## CRM

`products/caseforge-crm`; detail in its `README.md` and `TABS.md`.

A Next.js app with a search box, a results list and a detail panel. The browser talks only to the app's own server-side routes, and those routes alone hold the hub API token, read from the server environment. Fuzzy name matching happens in the hub API, not in the browser.

- **Edits.** "Edit client details" covers a fixed allowlist of single-value fields on people and matters (names, date of birth, NI number, contact details, structured address, the C8 flags, case notes, closing and reopening). A confirm dialog names every change. Edits apply at once, are attributed by a typed name, and are kept in a history list. Nothing is deleted, so a wrong edit is corrected by a further edit. The allowlist is enforced separately in the request schema, the hub and the SQL layer.
- **Several-row data** (parties, children) has its own row editors that write real rows and audit each change.
- **Quick-tick flags** live in the ops database and apply on click.
- **Demo mode.** With no hub API configured, `npm run dev` serves stub clients and shows DEMO in the header. `CASEFORGE_HUB_API_STUB=1` forces the stub.
- **Tests.** `npm test` runs vitest over the routes and library code. A test pins the firm defaults and fails on a firm value anywhere else in the app.

## Case flow

`tools/onboarding/pipeline/`; detail in its `README.md` and the `CASEFLOW-*.md` files beside it.

The pipeline takes a client from referral to a drafted email, through the court and service, round each hearing, and on to the closing letter. It appears as the Case flow tab in the CRM, with one button per step.

- **A step** is a module with `status(ctx)` and `run(ctx, variant, by)`. Status is always read from the live systems (the database, the client's folder, the sent folder), never remembered. Runs add files and never overwrite them. Each step says who acts next: `you` (a person), `case flow` (it runs, or waits on the court or a process server) or nobody.
- **The steps**, in outline: fetch the referral papers; check the record; make the folders; unpack attachments; prepare the witness statement; draft the client email with a signing envelope; make the court pack (Notice of Acting, FL401 or C100 and C1A, draft orders); draft the court email; file the court's reply; draft the papers to the client; request counsel; build the hearing bundle with a case summary and chronology; draft the papers for personal service and to third parties; file statements of service and draft them to the court; make the client care letter; draft the brief to counsel; draft the court-outcome letter after each hearing; and make the closing letter. `cd tools && python3 -m onboarding.pipeline steps` prints the current list with each step's number, actor and what it waits on.
- **Repeating steps** run once per occurrence: each court reply, each hearing, each statement of service.
- **Manual and auto.** Manual is the default and runs nothing by itself. In auto mode, `auto_pass(matter_id)` walks the chain in order, through the same `run_step` the buttons use, and stops at the first step that is not done, logging why. It never presses an override, never makes a second draft for a draft step that once succeeded, and acts only on matters opened after auto was switched on. With no switch-on time recorded it runs for nobody. A hold switch stops auto drafting without touching button presses.
- **Shared court and service code** (`court_common.py`) derives order codes from the order text (an unrecognised one asks a person), names files, finds court-order folders and makes drafts. Every draft is a fresh email, checked for placeholder text before it is made.
- **Address check.** Before a client draft is made, the address is scored against the client's name. A doubtful match is shown as advice on the step and in the run summary. It never stops the draft, because only a person sends.
- **Log.** Every run writes a `pipeline_events` row (matter, step, status, summary, who, mode, time) to the ops database.

## Court-form filling

`tools/documents/`.

- **FL401.** `fill_fl401_pdf.py` fills the official AcroForm from the matter record and the soft copy, with the record winning for text. The legal-representative block comes from the firm profile. The output can stay editable.
- **C100 and C1A.** `form_fill_pipeline.py` fills the forms from the client's witness statement in two model stages and a code check. A cheaper model extracts structured facts from the numbered paragraphs, with null for anything the statement does not state. A stronger model maps only those facts onto a catalogue of the form's fields. Code then works out the answers that follow from the facts (orders sought, children's rows, abuse boxes, incident rows) and applies the firm's standing answers.
- **The check in code.** An unknown field id is dropped. A tick is applied only for `true`. A value too long for its box is shortened or dropped. Every text value must appear in the statement or the facts, or it is reported as `ungrounded` and not filled. The report lists `filled`, `ungrounded`, `dropped`, `tbc` and `attention`, which is what a person completes.
- **AcroForm helper.** `pdf_acroform_fill.py` sets text and checkbox values, reading each checkbox's real on-state from the PDF instead of assuming `/Yes`.
- **C8.** `c8_protection.py` decides whether a client is C8 from the C8 text, the matter's flags, the FL401 or the statement, then empties the client's contact boxes and replaces their details elsewhere with `Withheld - see C8`.

## Document drafting

`tools/documents/`, `tools/counsel/`, `tools/onboarding/`; detail in the owning READMEs.

- **Witness statement.** `ws_cleanup.py` copies the client's account, without rewriting it, into the firm's statement template. It resolves Word auto-numbering to literal numbers, drops the original's address line, strips GPS data from embedded pictures and flags mismatched exhibits. Spelling, punctuation and grammar slips go through a small model behind a guard that applies only typo-level fixes and lists the rest. If the model cannot run, the statement is still saved, marked "spelling not checked", and left for a person.
- **Court heading.** `court_heading.py` builds the heading in code for every document that carries one, so there is one implementation.
- **Placeholder check.** `placeholder_check.py` refuses a draft whose subject, body or attachments still say TBC, TBA, "to be confirmed" or "to be advised".
- **Letters.** Client care letters are drafted, linted (`lint_letter.py --kind opening|closing|court-outcome`) and audited against their sources before a PDF, a signing envelope and a draft are made. Case summaries and chronologies read matter facts through one function that substitutes `TBC` for anything unknown and redacts C8 contact details before any renderer runs.
- **Bundles.** A hearing bundle is assembled from the papers on file into a draft PDF. A person's review bills its real page count.
- **Other outputs.** Notices of Acting, draft orders, attendance notes, statements of service, briefs to counsel, envelope sheets and email-to-PDF prints.

## Billing model

`tools/billing/`.

- `billing_items.py` keeps an itemised per-matter ledger (`matter_billing_items` in the ops database), one row per chargeable event with its own date.
- `record_item()` computes net and VAT amounts on the server from a fixed rate table (`CATEGORY_RATES`). A caller passes a category and a quantity or minutes, never a price. An unknown category raises an error.
- Per-unit categories cover letters, calls and pages, and hourly ones cover attendance, advocacy and travel. Bundles, court documents and documents received are billed per real page.
- Items are taken off a bill and restored, stamped with who and when, and never deleted.
- A matter's bill exports as a schedule grouped by category with totals, or as a 27-column register that `validate-billing-register.py` checks for missing fields and arithmetic. Register columns with no source yet are left blank and marked unreviewed, never guessed.
- The CRM's Billing tab shows the ledger grouped by category. It is not an invoice, because legal-aid matters are assessed rather than invoiced.

## Microsoft Graph

`tools/graph_mail_safe_ops.py`, `tools/graph_files.py`, `tools/graph_index.py`, `tools/mail_intake/`; detail in `tools/CORE.md`.

- **Mail.** `graph_mail_safe_ops.py` is the central mailbox wrapper. It is read-only by default, and writes need an explicit flag. `post_draft_payload` is the one place a draft is created: `POST /messages` with `isDraft: true`, never `sendMail`, always tagged `AI DRAFTED`.
- **Files.** `graph_files.py` normalises paths, uploads and downloads, and creates the standard client folder set. `graph_index.py` keeps a catalogue of OneDrive items in the ops database, so lookups do not need to list live folders.
- **Mail intake.** Graph posts change notifications to an Azure Function, which queues them. A worker on the server polls that queue outbound, so no port is open to the internet. The receiver stores only a message id. A separate classifier fetches the message, builds deterministic evidence from routing rules, the client database and the folder catalogue, assigns a route (court, counsel, client, complaints, legal aid, process server and so on) and matches exactly one live matter or none. Email content is evidence only, and a model comparison never overrides the deterministic folder choice. A reconcile job scans the mailbox directly to catch notifications the queue missed, using the same idempotency key so nothing is queued twice.
- **Hearings.** The calendar finder reads hearing notices from mail, binds each date, time and case number to one statement (reporting ambiguity instead of guessing) and records the hearing in the hearing store in clientdb. A hearing a person has edited is never overwritten by automation, and a disagreeing email raises a review flag instead.

## Client lookup

`tools/agwu/`; detail in its `README.md`.

Agwu is the single entry point for finding a client, a matter or a matter's folder: `resolve_client(query, caller=...)` and `resolve_folder(key, caller=...)`. It returns an explicit outcome, `resolved`, `ambiguous` or `not_found`, so an unattended job can tell "no such client" from "not sure". Its README states two rules every caller follows. A match score is not a confidence measure. And a matter id is never passed together with a live-fallback search. Every call is logged.

## Documenso

`tools/agents/documenso_envelopes.py`, `tools/documenso/`; detail in `tools/agents/onboarding_loa.README.md`.

A self-hosted Documenso instance holds the signing record. The REST client creates a document with the client as the single signer, uploads the PDF, places signature and date fields, and distributes it with `sendEmail: false`, then collects the signing link. Documenso has no mail server here: the link travels only inside an `AI DRAFTED` draft that a person sends. After each create, the envelope is read back and compared with what was asked for. When the client signs, a completion worker files the signed copy into the client's folder by the matter number carried on the envelope. For a client care letter it also records the billing. Callers are gated on `DOCUMENSO_API_ENABLED=1`. A nightly job backs up Documenso's database and stored documents.

## Models

`tools/model_backend.py`, `tools/model/`.

- Callers ask for a role named for its purpose (`case_summary`, `mail_triage`, `safety_guard` ...), not a model. Each role's model id is one line in `runtime-data/model-roles.env`, overridable per process by an environment variable, and changes on the next call.
- Casework calls go to OpenRouter. Every request carries `provider.zdr=true` and `data_collection=deny`, and a model with no zero-data-retention provider fails with an error instead of silently falling back to a provider that logs.
- `tools/model/zdr_check.py` sends a fixed one-token probe to every configured model and reports which still pass, because OpenRouter publishes no data-policy field to read.
- Every call writes a telemetry row (provider, model, outcome, elapsed time, prompt and response sizes, and which backend served it). A local llama.cpp backend is available as an explicit opt-in per role. It is never a default or an automatic fallback.
- Models read and draft. Code decides: a model never writes SQL, and every structured answer is validated in Python before use.

## Data stores

`tools/clientdb_sql.py`, `tools/ops_db.py`, `tools/sql/`.

- **clientdb (Postgres)** is the casework database: `people`, `matters`, `matter_parties`, `matter_children`, `matter_references`, `matter_hearings`, `attention_items` and related tables. `clientdb_sql.get_connection()` is the entry point. Schema changes are numbered migrations under `tools/sql/migrations/`, applied once each by `tools/sql/run_migrations.py`. A nightly `pg_dump` is uploaded to the firm's own storage.
- **ops DB (SQLite)** holds workflow state: Case flow events and saved step views, the billing ledger, matter flags, edit history, the durable job queue, the OneDrive catalogue and telemetry.
- **Change log.** A trigger on every client-data table writes each insert, update and delete to `clientdb_change_log`: the whole old and new row, the primary key, the changed columns, the actor, the application and the transaction id. Because the log lives in the database, no writer can skip it. The log refuses updates, deletes and truncation of itself, and if logging fails the write fails. A new table must attach itself, and a test fails on one that is neither covered nor listed as not client data. `tools/sql/change_log.py show` lists entries, and `revert` restores an entry or a whole transaction, as a dry run unless `--apply` is given. A revert is refused if the row has changed since, and is itself logged. The ops database has the same log (`ops_change_log`).
- **Retrieval.** A local Qdrant holds embeddings of folder metadata and, separately, of extracted matter content, for fuzzy lookup and fact search. The retrieval engine checks SQL first, then the content index, then a live folder listing, and always says which sources it checked.

## Workers, scheduling and monitoring

`deploy/systemd/`, `deploy/ansible/`, `tools/agents/`, `tools/monitoring/`; detail in the owning READMEs.

- Long-running workers (the mail-intake queue bridge, the classifier, the Documenso completion worker, the hub API, the CRM) are systemd services. Periodic jobs (the folder index refresh, reconcile scans, backups, health checks) are systemd timers or cron entries listed in Ansible group variables. Ansible provisions everything, so a rebuilt box has the same set.
- `tools/run_agent.py` and `tools/agents/job_queue.py` provide a durable job queue in the ops database.
- Shell wrappers share a job harness that takes a lock, writes a per-job log and pings a Healthchecks dead-man's switch, so a job that stops running raises an alert.
- `tools/monitoring/ops_supervisor.py` combines queue, service, startup, repository-maintenance, model-spend and other signals into one health snapshot that contains no personal data. The CRM's System health page shows it to administrators.
- New code reaches the server by an explicit deploy, a pull followed by a restart of the affected units. A timer runs the code checked out on the box.

## Telemetry

`tools/telemetry_sqlite.py`; detail in `tools/CORE.md`.

Runtime events, Graph calls and model calls are recorded in the ops database. High-volume heartbeats and successful fast Graph reads roll up into hourly counters. A maintenance command enforces retention. The health snapshots built from it carry counts, states and timings, not client names or message content.
